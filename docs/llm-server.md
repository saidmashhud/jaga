# Локальный LLM-сервер (srv2)

Runbook: как поднят self-hosted LLM для Cognitive OS и как его обслуживать.

**Хост:** `195.246.102.169` (srv2), Ubuntu 24.04, k3s control-plane — это боевой узел, поэтому всё запускается с жёсткими лимитами.

## Железо и что из него следует

| | |
|---|---|
| CPU | 24 vCPU, 2× Xeon E5-2670 v2 @ 2.5 GHz (Ivy Bridge, 2013) |
| Инструкции | AVX + F16C. **Нет AVX2, FMA, BMI2, AVX-512** |
| RAM | 62 ГБ (свободно ~41 ГБ; безопасный бюджет под LLM — 15–20 ГБ) |
| GPU | нет (только виртуальный VGA от QEMU) |
| Полоса памяти | ~19 ГБ/с (замерено) |

Отсутствие AVX2/FMA — определяющий фактор: генерация упирается в память, префилл в вычисления, и второе страдает сильнее.

## Сборка llama.cpp

**Главная ловушка:** готовые бинарники ollama/llama.cpp собраны под AVX2 и падают с `SIGILL`. Но и сборка с `-DGGML_AVX2=OFF` падает так же — виновата инструкция `shlx` в `ggml_cpu_init()`, а это **BMI2** (появился в Haswell, у Ivy Bridge нет). У llama.cpp для него отдельный флаг, включённый по умолчанию.

```bash
apt-get install -y cmake libcurl4-openssl-dev
git clone --depth 1 https://github.com/ggml-org/llama.cpp /opt/llama.cpp
cd /opt/llama.cpp

cmake -B build -DCMAKE_BUILD_TYPE=Release \
  -DGGML_NATIVE=OFF \
  -DGGML_AVX=ON -DGGML_F16C=ON \
  -DGGML_AVX2=OFF -DGGML_FMA=OFF -DGGML_BMI2=OFF -DGGML_AVX512=OFF

nice -n 10 cmake --build build -j6 --target llama-server llama-cli llama-bench
```

Диагностика, если снова упадёт с `Illegal instruction`:

```bash
gdb -batch -ex run -ex "x/1i \$rip" --args ./build/bin/llama-bench --help
```

## Сервис

- Юнит: `/etc/systemd/system/llama-server.service`
- Конфиг: `/etc/llama-server.env` (права 600, там же API-ключ)
- Модели: `/opt/models/`

Ограничения в юните защищают прод: `CPUQuota=800%` (8 ядер из 24), `MemoryMax`, `Nice=10`, `IOSchedulingClass=idle`.

⚠️ systemd подставляет переменные из `EnvironmentFile` **только в `ExecStart`**. `MemoryMax=${MEM_MAX}` не сработает — значение прописывается в юните явно.

```bash
systemctl status llama-server
journalctl -u llama-server -f
systemctl restart llama-server
```

Смена модели:

```bash
sed -i 's|^MODEL=.*|MODEL=/opt/models/Qwen3-30B-A3B-Q4_K_M.gguf|' /etc/llama-server.env
sed -i 's/^MemoryMax=.*/MemoryMax=24G/' /etc/systemd/system/llama-server.service
systemctl daemon-reload && systemctl restart llama-server
```

## Доступ

Слушает **только `127.0.0.1:8080`** — наружу порт не открыт. У llama-server нет полноценной авторизации, поэтому публиковать его на `0.0.0.0` нельзя.

Что закрыто ключом: `/v1/chat/completions`, `/props` → **401** без ключа.
Что открыто: `/health`, `/v1/models` (так устроен llama.cpp).

Подключение с рабочей машины — через SSH-туннель:

```bash
ssh -N -L 8080:127.0.0.1:8080 root@195.246.102.169
```

API OpenAI-совместимый, работает любой SDK через `base_url`.

## Замеры (8 потоков — оптимум; на 12 хуже)

| Модель | Префилл | Генерация | RAM |
|---|---|---|---|
| Qwen3-0.6B Q8 | 93 ток/с | 30.6 ток/с | 0.6 ГБ |
| Qwen3-4B Q4_K_M | 16.5–17.8 ток/с | 6.5–8.5 ток/с | 2.4 ГБ |
| **Qwen3-30B-A3B Q4_K_M** ← в работе | 21.8 ток/с | 9.8 ток/с | 17.3 ГБ |

Разбор заметки из ТЗ (блок 3.1) end-to-end: **9–30 с** в зависимости от сложности.

⚠️ Мерять только на прогретом кеше и без фоновых загрузок. Тот же 30B на холодную под активной докачкой показал 3.6 ток/с вместо 9.8 — мерился диск, а не модель.

### Выбор модели: 30B-A3B

Мини-эталон из 6 случаев (`/tmp/eval.py` на сервере, копия в scratchpad): ссылки по номеру, отсутствие срока, три сущности сразу, определение проекта по смыслу, смешанные ссылки, decision против task.

| Модель | Верно | Время |
|---|---|---|
| Qwen3-4B | 5/6 | 105.4 с |
| **Qwen3-30B-A3B** | **6/6** | **93.8 с** |

30B точнее **и** быстрее: MoE активирует лишь 3.3B параметров из 30B, поэтому по скорости он опережает плотную 4B. 4B провалил случай со смешанными ссылками — выдумал срок «в пятницу» там, где срока нет.

Цена — 17.3 ГБ RAM против 2.4 ГБ. На узле это допустимо (свободно ~41 ГБ), но помнить: лимиты RAM в k8s переподписаны на 152%, и llama-server будет крупнейшей целью OOM-killer. Держать `MemoryMax=24G` и следить за общим давлением.

Историческая заметка: первое сравнение делалось по одному примеру и дало обратный результат — по одному прогону выбирать модель нельзя.

## Правила использования (проверено на практике)

1. **Строгая схема — только через API.** `response_format: {"type":"json_schema", strict:true}` соблюдается точно. CLI-флаг `--json-schema-file` в этой сборке падает с `Failed to initialize samplers` — конвертор выдаёт GBNF, который парсер не принимает.
2. **Не давайте модели считать даты.** Qwen3-4B ошибается на день. Пусть возвращает `due_rel: "в среду"`, а дату вычисляет бэкенд.
3. **Держите системный промпт стабильным** — включён `--cache-reuse 256`. Повторный запрос переиспользовал 138 из 139 токенов, время упало с 23 до 16 с.
4. **Отключайте reasoning** у Qwen3: `/no_think` в конце сообщения, иначе модель тратит сотни токенов на размышления.
5. **Префилл — узкое место.** 1400 токенов контекста ≈ 85 с. В RAG отдавайте 2–3 коротких чанка после реранкера, а не 20.
6. **Проектируйте асинхронно.** Пространственный холст не обязан отвечать мгновенно: заметка принята сразу, узел появляется через ~20 с.

## Что установлено на сервере

Пакеты `cmake`, `libcurl4-openssl-dev`, `gdb`; каталоги `/opt/llama.cpp` (~1 ГБ) и `/opt/models`; юнит `llama-server.service` (автозапуск включён). Конфиги k3s не затрагивались.
